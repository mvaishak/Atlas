# M8 CPU profiling review v0.1

Status, 2026-11-05 Pacific: the approved DSMLP reference benchmark completed and its returned evidence passed independent verification. M7 is accepted. M8 lead acceptance, absolute performance ceilings and M9 study execution remain separate decisions.

## Scope and architecture

A hash-verified, development-only manifest selects 1,000 of 4,129 normalized query groups with seed 42. Query text stays private. The existing M7 artifact root and Python environment are reused without installing dependencies. The allocated CPU pod starts a supervisor, one uncached Uvicorn model worker and a separate HTTP client. There is no GPU or login-node model work.

Before load, the instrumented worker checks actual HTTP/offline feature and prediction parity using the frozen fitted model. It then runs BM25, M4 RRF and experimental M4/M6 reranking at concurrency 1, 4 and 8, three repeats each. Each trial has 100 sequential warmups and 1,000 measured requests. Pipeline order rotates by repeat; no failed request is retried. The original one-request inference admission and eight-connection server limit remain in force.

The benchmark wrapper forwards the original encoder recipe and returned arrays, recording calls without changing encoder source. Shared feature and prediction code remain responsible for ranking. Production timers separate feature construction, prediction and result ordering; benchmark-only timers expose the second feature query encoding. Stage boundaries overlap. HTTP dispatch includes request validation and threadpool dispatch; the client/server residual includes serialization and transport. Neither is a pure queue-time measurement.

## Alternatives

| Approach | Decision |
| --- | --- |
| Call retrieval helpers directly | Rejected for the load baseline: it omits HTTP admission, request validation and serialization. Helpers remain useful for correctness fixtures. |
| Trace every request with a native profiler | Deferred: it adds overhead and extra tooling. Lightweight stage boundaries establish the first bottleneck hypothesis; they do not establish exclusive CPU time. |
| Change admission while benchmarking | Deferred to a separately controlled study. The reference preserves existing failures and successful throughput. |
| Copy indexes or recreate the Python environment | Rejected: storage is limited and the existing immutable artifacts and pinned M7 environment already passed parity. |

## Compatibility, resources and failures

The explicitly authorized M7 Linux portability policy is retained: the historical recipe digest and actual DSMLP digest are distinct. Only the Linux platform string may differ. The historical recipe is reconstructed metadata with an exact sealed-digest match, not a recovered original file. Scoring fields, model/dependency pins, feature boundary and immutable components remain exact; see [M7 review](M7.md).

The official launcher sets CPU request 2 / limit 4 and memory request 16 GiB / limit 32 GiB. The pod has no GPU resource. CPU limits are shared-node quotas, not reserved physical cores. Available-memory admission is 8 GiB, process-tree sampled RSS and worker high-water limits are 12 GiB. The supervisor includes its own RSS and children, with a nominal 0.1-second sampling interval and a shutdown reserve. Sampling does not prove every transient allocation was observed.

Storage uses the smaller of filesystem free space and a conservative 4 GiB baseline derived from the user's approximately 5 GB quota headroom, subtracting all new M8 files. Filesystem capacity is not the user's remaining quota. The cap is 1 GiB new files and 2 GiB estimated remaining headroom. Final evidence files must be counted independently because the supervisor's recorded byte count precedes its final result/checksum writes.

The first launcher submission failed on an admission-webhook timeout before a pod existed. The retry used the same official generated pod specification and succeeded. Both submissions and the original absolute cumulative deadline are preserved. There was no environment change or budget reset.

Concurrent rejection remains a baseline outcome. Report application `pipeline_busy`, Uvicorn `server_concurrency_limit`, timeouts and unexpected errors separately. Success latency is conditional on admission; admitted query subsets can differ under overload. Fast rejection percentiles cannot demonstrate fast inference.

## Proposed M9 study and absolute limits

Pending lead approval. The candidate intervention is request-scoped reuse of the already computed query vector when constructing M6 features. Keep the original reference path and one separately identified variant. Bind a reused vector to the normalized query and full encoder provenance; reject the wrong query/recipe, preserve float32 shape/normalization and prevent mutation. The HTTP caller cannot supply vectors. No vector survives the request. Encoder code, model weights, index, candidate depth, RRF constant, precision, native threads and admission policy remain fixed.

The alternative of an approximate index addresses dense lookup cost but introduces index/recall/storage changes. Changing candidate depth alters relevance; changing precision alters numeric compatibility. Those are separate factors and are excluded from this bounded study. Query reuse tests a directly observed duplicate computation with minimal new storage.

Proposed execution budget: 4 CPUs/32 GiB/no GPU, 4 cumulative hours including setup/retries, at most 1 GiB additional persistent files, at least 2 GiB conservative remaining quota headroom, 8 GiB available memory and 12 GiB RSS. Reuse existing artifacts and environment. Only small code/manifests and the locally available development inputs need transfer.

Compare the reference and one reuse variant on the same 1,000-query load workload, 100 warmups then 1,000 measurements, concurrency 1/4/8 and three interleaved repeats per variant. On all 4,129 development queries, compare actual feature matrices, dtypes, masks, alignment, candidate membership, predictions and final rankings; compute A/B/C development metrics with the existing evaluator and preserve unknown-label caveats. Stream compact equality receipts and retain explicit mismatch evidence. Any mismatch rejects the variant. Test judgments remain locked. No training or new index is authorized by this proposal.

| Proposed criterion | Limit before executing M9 |
| --- | --- |
| Minimum worthwhile improvement | At least 15% reduction in successful concurrency-1 M6 p95 in each paired repeat; report all other quantiles and throughput. |
| Absolute concurrency-1 p95 ceilings | BM25 20 ms; RRF 400 ms; M6 500 ms on this declared CPU workload. These are proposed review limits, not portable service guarantees. |
| Correctness and quality | Exact reference/variant feature and prediction parity; invariant candidates/rankings and zero A/B/C metric change. Any changed result rejects reuse. |
| Errors and timeout | Zero concurrency-1 errors and timeouts; zero unexpected errors and timeouts at every tested concurrency; retain the 30-second timeout. |
| Concurrent stress | Publish all rejections, admitted subsets, success throughput and latency. The current admission policy is unchanged; no production concurrency/SLO claim follows from this study. |
| Startup and memory | At most 120 seconds to readiness; 12 GiB RSS ceiling and 8 GiB available-memory gate retained. |

Keep the reference when improvement, correctness or resource criteria fail. This study can satisfy the required optimization experiment even if the variant is rejected. It cannot promote the negative-C M6 ranker or establish portfolio completion. Lead approval of the concrete limits, scope and budget is required before any M9 variant execution.

## Human review and interview checks

1. Why separate all-request and success latency? Rejections complete quickly, so their percentiles can hide slow inference. Inspect counts, successful throughput and admitted-query composition together.
2. Why can stage timers not be summed? Feature construction contains the second encoder call; existing aggregate timings contain nested stages. Compare exclusive boundaries only when actually measured.
3. What does exact parity prove under the platform exception? It establishes the tested feature/prediction boundary and records both runtime identities. It does not establish identical operating systems or universal portability.
4. Why can better Track A NDCG coexist with worse C? Track A ranks labeled candidates, while C retrieves from the catalog with incomplete judgments and a restricted candidate pool. Preserve both results.
5. What would justify an encoder-reuse optimization? Repeated profiles must establish its cost, then an approved one-factor comparison must preserve exact features, predictions, candidates, quality and resource limits.

Before acceptance, the lead should inspect raw-to-summary validation, overload failure counts, timer boundaries, resource limits and the saved-versus-live evidence distinction. Generated answer outlines do not establish human understanding. Absolute performance ceilings and the next study's budget/adoption criteria still require the lead's decision.
