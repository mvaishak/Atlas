## Alternatives and decisions

1. **Reuse package supervisor and thin notebook** versus a notebook-specific encoder: selected shared modules so weights, tokens, normalization, chunk identity and numerical gates remain inspectable and testable. The cost is strict runtime compatibility and setup failure on native-library drift.
2. **Immutable per-chunk ZIP plus receipt** versus one giant embedding file or relying on Drive rename: selected receipts to recover acknowledged chunks without trusting unsupported atomic filesystem semantics. Compression/checksum/Drive I/O add overhead and partial uploads consume space.
3. **Stream returned receipt ZIPs** versus fully expanding another compressed checkpoint tree: selected streaming to keep the proposed Mac disk budget plausible while retaining the untouched downloaded archive. Native FAISS is reconstructed locally, so full build/load memory remains a Mac risk.
4. **Conservative first-allocation wall anchor** versus trying to infer GPU billing from successful Python time: selected the upper bound to cover idle/retry gaps. It can overcharge disconnected downtime and block otherwise affordable recovery; extending budgets requires lead review.

Five interview questions and answer outlines:

1. **Why is a checksum receipt the commit point?** A ZIP without a receipt may be incomplete. Only reread, verified bytes plus an immutable receipt are resumable. Ephemeral-only sealed chunks may be re-encoded after VM loss.
2. **How is identity alignment proved beyond vector count?** Pin source bytes and canonical order, then validate exact product identities/titles and content hashes for every chunk/range. Equal counts alone cannot detect permutation or wrong titles.
3. **Why can cross-device rankings differ?** Float32 kernels can differ within approved error bounds. Compare components/cosines, report memberships and near ties, and reject materially separated inversions. Do not round scores or redefine metrics.
4. **Why separate GPU and Mac ledgers?** Original GPU job lineage stays immutable. CPU FAISS and development work consume their own two-hour budget rather than adding CPU time to historical GPU attempts. Both include failures/retries.
5. **What does the pilot establish about a five-hour full run?** It establishes bounded compatibility/numerical behavior and one observed rate. Extrapolation lacks catalog-length distribution and large Drive history evidence; enforce caps and preserve negative/incomplete results rather than claiming completion in advance.
