## Existing service and smallest useful outcome

Reuse `src/atlasrank/serving/app.py:create_app`. It already owns one immutable BM25
bundle in process and exposes:

| Route | Existing behavior |
| --- | --- |
| `POST /search` | Strict `{query, top_k, locale}` input; US only; top_k 1–100; IDs, titles, scores, pipeline/bundle IDs and measured search time |
| `GET /health/live` | Process liveness |
| `GET /health/ready` | Validated index readiness; 503 when unavailable |

Search validation rejects empty/tokenless/oversized input, unsupported fields and
invalid types. OOV queries return an empty list. Errors use safe explicit codes.
Structured logs exclude raw queries and product IDs. Startup validates the index and
retains the existing 6 GiB process ceiling. `tests/test_search_api.py` already checks
HTTP/offline equality, invalid requests, missing/corrupt bundles and safe errors/logging;
those tests passed in the fresh integration group.

Recommendation: add one small HTML view to this same FastAPI app. First expose the
already working live BM25 search with top-10 titles, IDs, scores, bundle version and
actual request/search timing. Add a bounded saved-development comparison in the same
view using the local, accepted M3 BM25 and M4 pretrained-hybrid results. That provides
a real two-pipeline comparison without loading Torch/FAISS together on the Mac or
rebuilding any index. Keep the existing search endpoint and CLI behavior compatible.

The comparison is explicitly a replay of recorded retrieval for selected development
queries. It must not imply arbitrary-query live neural inference. Historical M4
per-query records contain rankings and scores but **no per-query retrieval timings**;
show that timing as unavailable. Current API/report-load timing can be measured and
labeled separately. Never present it as historical model latency or a benchmark.

M5 can appear in a sourced aggregate development-results table with its limitations.
Do not fabricate M5 top-10 lists from compact recalls. A future M5 replay pane requires
an independently checked small extract of original rankings from private Drive; it
would not require downloading the full index. Live M5 search additionally requires
native bundle validation and a compatible runtime, outside this proposed first slice.

## Proposed implementation sequence and interfaces

1. Preserve the current `create_app(index_path)` factory, startup, request validation,
   readiness/error behavior, BM25 adapter and loopback serving command. Add an optional
   read-only comparison fixture to that app, rather than a second API or UI server.
2. Prepare a private, small allowlisted set of development examples from the frozen M4
   `per-query.jsonl`, matching report/provenance and approved catalog. Stream only the
   selected records; preserve their Track B top-10 order and scores. Resolve titles from
   canonical product identities and attach development judgments using the guarded
   loader. Unjudged results remain `unknown`. Labels never filter candidates.
3. Save a new ignored fixture with source hashes, query/group IDs, product identities,
   titles, original scores, pipeline/bundle IDs and judgment status. Do not modify the
   frozen M3 index, original reports, model files or historical artifacts. Keep query
   examples private; version source/schema and a synthetic fixture instead.
4. Proposed added routes: `GET /demo` for the single view and `POST /comparison` with a
   strict allowlisted `query_id` and a fixed top-10 response. Return the two recorded
   pipelines plus explicit `mode: saved_development` and source identifiers. Free-text
   BM25 requests continue through `POST /search`. Reject unknown IDs rather than
   returning an unrelated saved example.
5. The HTML uses the same origin and routes, with no duplicated search, embedding,
   fusion, metric or label-processing code. Distinguish loading, empty results,
   unavailable comparison data and service errors. Display score types separately:
   BM25 and RRF scores do not share a scale. Missing optional comparison data disables
   that capability explicitly while the existing BM25 path remains available.
6. Verify synthetic API/report parity and one bounded actual-example check after
   implementation approval. No full development evaluation is needed for this UI.

Proposed files, subject to implementation approval:

| File | Purpose |
| --- | --- |
| `src/atlasrank/serving/app.py` | Extend the existing application and state with optional read-only replay support |
| `src/atlasrank/serving/comparison.py` | Validate/load the small fixture and return recorded results; no inference or fusion implementation |
| `src/atlasrank/serving/static/demo.html` | One plain HTML/JS view, served by the same app |
| `scripts/prepare_demo_examples.py` | Bounded extraction/join/hash checks using existing contracts and guarded development loader |
| `tests/test_search_api.py`, `tests/test_demo.py` | Existing API compatibility and new fixture/display/provenance checks |
| `docs/reviews/M6.demo.md` | Implementation evidence, commands, measured timings and remaining limits |

No dependency addition is proposed. Packaging would include the single static asset
in the existing package. Do not introduce Streamlit, a separate frontend service,
a model registry service, a generic plugin framework or cloud deployment.

## Alternatives and resources

| Option | Engineering/resource impact | Decision |
| --- | --- | --- |
| Existing BM25 endpoint plus a view | Smallest change; no neural runtime; arbitrary-query search works with existing index | First visible increment |
| Same view plus saved M3/M4 development comparison | Uses available actual rankings; tiny runtime fixture; explicit replay semantics | Recommended complete first demo slice |
| Live BM25/M5 dense/hybrid on the Mac | Requires missing original artifact verification and unresolved native runtime compatibility | Defer; do not repair Mac dependencies here |
| A second API, separate frontend server or Colab serving | Duplicates integration/deployment work and adds runtime coupling | Reject for this slice |

Resource estimates are proposals, not measurements: zero GPU time, no model or dataset
download, no training/re-encoding. Target five pinned comparison examples and a fixture
under 1 MiB; do not load the complete historical per-query report into the serving
process. Preserve the current 6 GiB server ceiling. Bounded fixture preparation should
stream selected records and select only required title rows; stop if it requires a
full index rebuild or another environment. Measure actual startup/RSS and request
latency during a small future smoke check; make no throughput/SLA claim from it.

A proposed operator command after implementation remains the existing one:

```sh
# Open http://127.0.0.1:8000/demo after that route is implemented.
```

The command was inspected, not run as an M6 experiment. There is no new service launch
in this planning task.

## Acceptance, limitations and milestone boundary

- One FastAPI process and one view; the existing `/search` contract still passes.
- HTTP BM25 results exactly match offline adapter identities, scores and ordering,
  including Unicode normalization, ties, OOV input, short lists and serialization.
- Replay results match the pinned source record exactly in identities, order, score
  values, titles and judgment status. Deliberate source/model/bundle mismatch or corrupt
  fixture fails closed. Query IDs and normalized groups must match approved development.
- Displayed pipeline/bundle versions, source mode and measured timing fields are checked
  against actual API/report output. Missing original timing is visibly unavailable.
- Input text is safely rendered, not inserted as executable HTML; logs continue to omit
  raw queries. No test data, accounts, publication, new services or expensive jobs.
- M5 missing original-artifact verification and M4/M5 preprocessing/normalization/tie
  differences remain documented; a small demo does not resolve or conceal them.

The roadmap's full M6 is **learned ranking and exact feature parity**. This demo-first
proposal is a bounded integration slice, not a claim that M6 is complete or permission
to train XGBoost. Its later ranker work must retain exact offline/HTTP feature names,
ordering, dtypes, missing masks, product alignment and values immediately before
prediction. Existing BM25 parity tests do not satisfy that future learned-feature gate.
The roadmap's larger M7–M10 operations, optimization, final evaluation and portfolio
requirements remain intact. No evaluation definition or milestone exit was rewritten.
