## Architecture and data flow

`configs/esci.json` pins the official revision, six file sizes, and SHA-256 hashes. `data-acquire` runs a monitored worker, verifies each source, and preserves immutable raw files. `data-prepare` verifies them again, streams catalog text in 8,192-row batches, projects query/product identities, joins only official-train labels, creates connected query groups, quarantines overlap, assigns the approved hash split, and writes checksummed manifests plus a completion marker. [DATA.md](../DATA.md) defines schemas and reproduction commands.

The public judgment loader accepts only completed train/development outputs and verifies schema/hash compatibility. Test rows remain in a label-free reference manifest backed by the unchanged raw file. The full US catalog includes held-out-query products, as required by the fixed-catalog evaluation design. The metric functions accept explicit judgments, rankings, and catalog identities; no data loading or model scoring is hidden inside them.

The controller samples child RSS every 0.1 seconds and checks disk every second, stopping on budget violations while preserving files and an execution record. Raw acquisition is about 1.08 GiB; the final preparation pair stayed below 1.12 GiB sampled child peak RSS. This is a local data-contract check, not an inference benchmark.

## Metrics, conformance, and supervision

The implementation preserves linear gains E/S/C/I = 1/0.1/0.01/0, full judged-pool IDCG, E-only reciprocal rank, known-exact recall denominators, unknown-label coverage, and returned counts. Empty rankings, no-E queries, zero IDCG, short results, invalid labels, unknown/duplicate IDs, and ascending product-key ties are tested. Track A rejects incomplete candidate sets; fixed-pool membership checks reject lost/duplicated candidates. Paired intervals use 2,000 normalized-group resamples, seed 42; slice summaries report query and recall denominators.

[Static metric fixtures](../../tests/fixtures/metrics.json) include independently calculated expectations, also verified with 60-digit Decimal logarithms. `docs/reviews/M2.xgboost.json` (private evidence) records a CPU, zero-tree `rank:ndcg` Booster with fixed labels/margins, multiple groups, reversed rankings, ties, cutoff truncation, and zero IDCG. No training, update, prediction, or saved model occurs. Actual objective configuration confirms `ndcg_exp_gain=0`. `ndcg@10-` matches the contract; default `ndcg@10` adds 1 for the zero-IDCG group. Default exponential gain rejects label 100, detecting the incompatible default explicitly. This probes evaluator semantics; objective gradients/updates remain M6 work.

Supervision fixtures allow only a training query's E positives and explicitly judged I negatives. They exclude S/C, unknown and other-query candidates, and held-out partitions; handle multiple E, duplicate/conflicting judgments, and missing E/I. The helper reports unusable groups without sampling. Actual sampler/loss behavior, negative-mask contributions, finite loss/gradients, and checkpoint restoration remain unimplemented M5 gates.

## Failure modes and residual limits

- A changed source, partial download, bad schema, missing join, unknown train label, or conflicting train pair fails validation. Raw files remain intact; partial outputs lack a valid completion marker. Recovery uses a new destination after review of the cause.
- Group leakage can arise from Unicode/text variants or transitive identity connections. Connected-group fixtures, output-boundary assertions, and frozen hashes detect these exact cases. Paraphrase/variant leakage remains possible.
- Test isolation is procedural. The single source row group may contain train/test label pages together; application projection prevents returned test labels, but raw files remain technically readable. No test quality, label distribution, or label-conflict claim is made.
- The 0.1-second memory monitor can miss transient spikes; it isn't a hard OS allocation limit. Observed peaks leave substantial headroom. More retained runs still consume the 30 GiB budget; stop rather than delete history to continue.
- Ignore rules don't stop force-adds or protect already-tracked files. The old `data/` pattern also hid source code; anchoring `/data/` and `/artifacts/` preserves code visibility while excluding designated runtime storage. Future staging still requires review.
- Local CPU XGBoost/NumPy/OpenMP execution passed. Linux CPU-wheel metadata isn't execution evidence; Linux runtime/ABI/CI remains unverified. No GitHub Actions ran.
- Metric fixtures don't establish model quality; zero-update conformance doesn't establish ranker gradients. Supervision fixtures don't validate a future sampler/loss. No retriever, model, benchmark, or final test evaluation ran.

## Five technical interview questions and answer outlines

1. **How can query-ID-only splitting leak, and how does the connected grouping prevent it?** A query ID can have multiple text variants and text can connect different IDs. Union both relations transitively, quarantine the entire component on any test overlap, and hash its smallest normalized text once.
2. **Why keep unknown products in C's ranking and use the full judged pool for IDCG?** Removing unknown positions compresses ranks; using retrieved-only IDCG hides missed positives. Unknowns have zero observed gain for this pooled calculation, with coverage and incomplete-judgment caveats reported separately.
3. **What did the XGBoost check actually prove?** Fixed margins with zero boosted rounds confirm linear NDCG ratios, ties/cutoff fixtures, actual objective configuration, and the `ndcg@10-` zero-IDCG adapter. It proves neither fitting nor useful gradients/model quality.
4. **Why can a product judged I for another query still be forbidden as a negative?** Relevance is query-specific. Only this training query's explicit I is admissible; other E positives, S/C, unknowns, and held-out judgments are excluded. Missing E/I makes the group unusable.
5. **What do identical output hashes and the memory monitor guarantee?** They show deterministic preparation for the pinned files/configuration/dependencies and observed local resource use. They don't prove cross-version byte identity, semantic label correctness, hard memory isolation, Linux behavior, or future model/index fit.
