## Architecture and data flow

A sealed serving descriptor references original lexical/dense/model/config/ranker components beneath an explicit artifact root. Native-free preflight verifies the descriptor identity, exact component inventory, external manifest pins, relative paths and absence of symlinks. Original component loaders then check checksums, dependencies, index reconstruction/norms, catalog alignment, tokenizer/model files and feature provenance. Every neural pipeline independently checks the approved CPU query-recipe digest. A descriptor alone isn't proof of native compatibility.

The existing application factory loads one runtime at startup. Complete-bundle startup failure keeps all configured inference unready. Legacy BM25 and its optional fixed-candidate fixture mode retain their old behavior outside complete-bundle mode. `/search` explicitly selects BM25, M4 dense, M4 RRF or experimental M6 over unchanged retrieval-100/RRF-60 pools. Both complete-runtime `/search` and `/rerank` use the same nonblocking admission lock and memory admission check. No labels enter live ranking.

Original shared feature construction and final prediction conversion are reused. The pipeline fixture reaches the real HTTP `/search` path, independently constructs the offline pool, and compares exact feature names/order/dtypes/masks/identities/values inside the predictor. An injected HTTP feature defect is detected. No tolerance was added to the exact boundary.

Responses expose score type, selected pipeline, component versions, request identity, candidate counts and observed stage timings. The default is BM25. M6 remains experimental after its negative pooled C result. Live execution, deterministic fixture execution and saved comparisons have separate labels.

Request bodies are bounded at 16 KiB before parsing. Existing query/top_k limits remain 512 characters, 128 analyzer tokens and 1–100. Structured JSON logs omit payloads and exception strings. Dependency-free aggregate metrics use bounded route/status and pipeline/stage labels. One CPU worker admits one inference request at a time. Overlap receives 503 and Retry-After. M8 will measure the quality/performance consequences. No throughput claim is made here.

## Alternatives and decisions

| Alternative | Decision and cost |
| --- | --- |
| Separate retrieval/ranking services | Rejected. Network boundaries add complexity without measured need. One modular process preserves original architecture. |
| Copy full artifacts into a serving image | Rejected. Seal references and mount immutable inputs read-only. Image builds contain only allowlisted source and dependencies. |
| Promote M6 after its Track A gain | Rejected. Keep explicit experimental selection and retain RRF/BM25 references. |
| Concurrent native inference immediately | Rejected for this reference. Shared admission bounds overlapping allocations and prediction state. This limits throughput and can cause busy responses. Measure in M8. |
| Require full platform identity for every environment | Retained as the default. The subsequent DSMLP run explicitly permits only the Linux platform string to differ, while recording actual provenance and enforcing all scoring/dependency pins plus real HTTP parity. |
| Add a metrics package | Deferred. Bounded counters/sums/counts use the existing stack. Benchmark percentiles remain a separate experiment. |

The full query encoder runs once for retrieval and again through the existing shared feature path during reranking. This preserves that path's contract. M8 should profile the cost before proposing any reuse optimization. Feature and prediction timings are currently combined rather than pretending to have separately measured them.

## Interview and human-understanding checks

1. Why separate liveness and readiness? The process can answer health requests while artifact validation has disabled inference. Trace descriptor loading and a corrupt-component failure.
2. How does a descriptor prevent mixing models/indexes? External manifest pins plus existing component checks bind identities, recipes, catalog content and schema. Explain why hashes alone don't prove semantic vector alignment.
3. Why compare predictor inputs exactly? Approximate outputs can hide dtype, explicit-zero, missing-mask or ordering defects. Trace offline pool construction through the actual HTTP predictor boundary.
4. Why serialize requests here? Native model state and full-catalog allocations are shared. Explain the common search/rerank lock, overload response, memory failure transition and the throughput cost.
5. Why keep M6 experimental? Its judged-candidate gain coexists with a negative pooled retrieved-candidate result. Explain sparse judgments, fixed candidate membership and the limits of the observed regression.
