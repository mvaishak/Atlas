## Architecture and interfaces

The existing module boundaries are retained. A new canonical identity/title projection sorts the approved M2 catalog to the same product-key order as M3. `retrieval/chunks.py` streams fixed batches into immutable, sealed chunks and records cumulative attempt time. `artifacts/dense.py` provides exact inventory, checksums, schema and canonical identity checks. `retrieval/dense_bundle.py` assembles a normalized matrix, product mapping and native exact FAISS index, then verifies every reconstructed row against the saved matrix before use.

`retrieval/dense.py` supplies deterministic whole-catalog search and native subset cosine scoring. `retrieval/comparison.py` uses the existing metric/slice/uncertainty functions for guarded development-only BM25/dense/RRF comparisons. `retrieval/full_run.py` provides a separately gated CPU supervisor; its complete full worker hasn't run. The [dense contract](../DENSE.md) documents files, failure/recovery behavior, commands and scope. No new package, service, training pipeline, ranker or architecture expansion was introduced in this infrastructure substage.

The CPU recipe remains title-only NFKC/casefold/whitespace normalization, uncased WordPiece, right padding/truncation to 256, attention-mask mean pooling and L2 normalization, float32, batch 32, query batch 1, eager attention, seed 42 and 1 thread. ## Immutable chunks and verified resume

Chunks contain only products, vectors, manifest and completion marker. Their identity binds source/job/recipe, row interval and component hashes. Source rows/titles, normalized vector shape/dtype/norm and global key order are checked. Fixed chunk boundaries align with encoding batches. Files are staged privately, flushed/fsynced, sealed and atomically renamed under a nonblocking writer lock, then kept read-only. Application code never replaces a committed chunk.

Resume validates and skips complete chunks, preserves incomplete partial directories, and rebuilds only missing chunks in new locations. Changed source/recipe/origin/batch boundaries/budget or in-flight encoder changes fail closed. Start/end/recovery records accumulate failed and resumed time; an unclosed attempt conservatively charges elapsed wall time through recovery, including downtime. A long outage or clock reversal can exhaust the budget and require review; accounting never silently resets.

Infrastructure evidence (`docs/reviews/M4.infrastructure.json`, private evidence) records the bounded 64-row, 384-dimensional saved-pilot replay. It uses previously encoded vectors and clearly synthetic fixture judgments, with **no new model inference and no real relevance labels**. The first fixture used an injected exception; the follow-up terminated its own child with SIGTERM during the second chunk (return code -15), leaving one complete chunk and one abandoned partial. One unclosed attempt was recovered. Resume skipped the complete chunk without changing its bytes or modification times.

Both resumed and uninterrupted builds produced identical chunk IDs and **all 5 bundle files byte for byte**. The artifact ID is `1454cc0a0716dc9c7d5b09e8c79baf868ad8d5f00611b307b9e415b8cca0a977`. Mapping, native subset scores, repeated search and saved-index search agreed exactly on this fixture. The interrupted partial and both earlier infrastructure runs remain intact. This demonstrates process-interruption behavior on a bounded fixture; it doesn't establish full-catalog performance, power-loss recovery or actual-model bitwise re-encoding across hardware.

## Bundle integrity and compatibility

Dense bundles contain `products.parquet`, `vectors.npy`, `index.faiss`, `manifest.json` and `COMPLETE.json`. Their schema binds source/chunk lineage, recipe, versions, counts/dimensions, dtype/metric and hashes. Loading checks exact inventory, symlinks, compatibility, unique canonical US identities, nonfinite/non-unit vectors, native index type/count/dimension/metric and exact reconstructed-vector row equality in bounded blocks. Lexical/dense keys and titles must also match the same pinned source before evaluation.

Tests reject missing/corrupt/extra components, changed model/backend recipe/origin/version, wrong native index type, reordered FAISS rows, bad norms, duplicate identities, symlinks, corrupt committed chunks and rehashed source-title changes on resume. Writer contention and in-flight recipe mutation fail before publication. Checksums/read-only files assume trusted local artifact selection; they aren't signatures or a hostile-upload boundary. A self-consistent malicious replacement isn't authenticated by a local manifest.

## Development-only evaluation protections

The evaluator wrapper checks audit/catalog/development hashes, job/bundle/encoder lineage and lexical/dense identities/titles before calling the guarded development loader. It has no split argument. No test references/raw examples are read. Query IDs must have consistent text/group, unique product pairs and a nonempty development partition.

Track A scores **every** supplied judged product with BM25 and native dense cosine, then fuses their complete judged-pool rankings with RRF-60. Track B independently retrieves 100 dense neighbors and up to 100 BM25 positive matches, deduplicates the union, and keeps 100 fused products. Labels never select retrieval candidates. The existing gains, NDCG/MRR, known-exact Recall@20/@100, unknown judgment coverage, zero-IDCG/no-E handling, slices and 2,000-resample/seed-42 normalized-query-group paired intervals are reused unchanged. Reports preserve per-query IDs, scores, ranks, bundle/source/recipe hashes, counts and exclusions; raw query text stays out of those records.

Fixture tests show A retains 110 judged candidates while B retains 100, OOV BM25 returns an empty list, unknown retrieved products keep their positions, zero-IDCG queries remain included and no-E recall stays undefined with exclusions. Paired dense-minus-BM25, hybrid-minus-BM25 and hybrid-minus-dense comparisons execute on fixture development inputs. A separate check requires exact M3 per-query BM25 metrics, identities and scores, excluding timings; an injected score change fails it. The full worker pins the actual M3 development output for this later check. **Real dense/hybrid development comparisons haven't run**, and synthetic fixture scores aren't catalog quality evidence. ## Design alternatives

| Decision | Alternatives and choice |
| --- | --- |
| Input ordering | Original metadata order versus canonical product-key projection. Canonical order matches M3 and makes row/vector identity explicit; the original catalog remains intact |
| Checkpoint unit | One giant array versus fixed immutable chunks. Bounded chunks permit skip/retry and preserve partial failures; chunk/hash/fsync overhead remains to be measured at scale |
| Publication | In-place mutation versus staged, validated atomic rename under a writer lock. Completed chunk files and manifests are never replaced by the application |
| Dense validation | Hashes only versus hashes plus native reconstruction and mapping/recipe checks. Structural and exact row checks catch compatible-looking but misaligned artifacts |
| Retrieval scoring | NumPy candidate dots versus the pinned native subset-distance primitive. Native scoring shares the FAISS cosine implementation; the separate cross-kernel tolerance diagnostic remains distinct |
| Execution backend | Measured CPU reference versus unmeasured MPS/Colab. CPU is the current full-run recommendation; optional accelerator experiments need separate approval |

## Failure modes and remaining limitations

- Corrupt committed chunks or incompatible recipes fail; incomplete partials remain preserved and are re-created elsewhere. A large failed bundle may exhaust the 8 GiB allowance, requiring review instead of deletion.
- A crash during the initial canonical projection or control-file creation can leave an incomplete control artifact that fails closed and needs operational review. Process SIGTERM was verified; power loss/disk failure wasn't simulated.
- Read-only files, advisory locks and checksums are local application controls, not hostile multi-user isolation or signatures. Native FAISS is loaded only after trusted local integrity checks.
- The actual long-running model, full catalog, whole supervisor lifecycle, Linux runtime/CI, MPS, Colab and serving integration remain untested. Current end-to-end infrastructure evidence uses synthetic encoders and saved-vector replay; cross-machine actual-model bitwise resume isn't established.
- Full-catalog quality, paired real development deltas, complete pre-ranker candidate reports, training, learned reranking and final test evaluation remain unrun. No promotion, M4 completion or M5 authorization is claimed.

## Five technical questions and human checkpoints

1. **What exactly makes a chunk reusable after interruption?** A completed manifest, exact source identities/titles/row bounds, unchanged encoder/runtime recipe and verified file/vector hashes. Partial directories never qualify.
2. **Why can resumed and uninterrupted artifacts match byte for byte while their logs differ?** Batch/chunk boundaries and numerical inputs are fixed; artifact identity excludes paths/timings/attempt IDs. Attempt/recovery logs retain separate operational history and cumulative charges.
3. **Why validate native reconstructed rows in addition to checksums?** A correctly rehashed but wrong type, shape, norm, mapping or reordered index is structurally incompatible. Exact row comparison links native scores to saved vectors; it doesn't authenticate a hostile replacement.
4. **Why does A retain more than 100 candidates while B doesn't?** A measures conditional ranking of the entire judged pool. B measures actual catalog retrieval with fixed budgets; injecting judged positives or removing unknowns would change the contract.
5. **What does the CPU pilot justify about accelerator choice and the full budget?** It provides one measured rate/memory observation and a transparent extrapolation. It doesn't establish MPS/Colab speed, runtime availability, sustained throughput, full-catalog fit or quality gains.

The lead should trace a key through canonical input, chunk, saved matrix, FAISS row and A/B lists; inspect in-flight recipe/lock/recovery tests; recompute vector/storage/time budgets; explain unknown-label denominators and paired group sampling; and review the explicit execution gate before approving a full run. Human understanding/code/resource approval remain pending, rather than self-asserted.
