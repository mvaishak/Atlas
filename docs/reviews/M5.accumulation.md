## Implementation and regression evidence

The training loop splits each frozen effective window into eight-group microbatches. It backpropagates each independently, weighting its mean loss by `microbatch_groups/effective_window_groups`. Thus a full window is 8/16 + 8/16; the final twelve-group window is 8/12 + 4/12. It zeros gradients once, clips once after accumulation, and performs one optimizer/scheduler update. The original AdamW, precision, seed, supervision, temperature, model and tokenizer remain unchanged. The diagnostic uses the original 574-update scheduler horizon (29 warmup updates), but can execute at most ten updates. Changed dropout batching is not bitwise equivalent to the original batch-16 trajectory.

Every window/microbatch emits scalar-only records at window start, before/after forward, after backward, before update and completed update. Records include committed step/cursor, attempted window, microbatch index/group/text counts, finite-or-null loss and gradient norm, LR, timing/throughput, driver free/total VRAM, Torch allocated/reserved/current-window peak/cumulative peak, host available RAM and RSS. CUDA phase synchronization makes measurements interpretable; diagnostic throughput includes synchronization and durable logging overhead. No graph-attached tensors are retained in history.

`DurableEvents` flushes and fsyncs before returning. Completed-update evidence is written before the post-update memory guard. Exceptions produce terminal failure events with the last committed cursor and attempted phase; partial windows are not marked committed. The runner closes logs in `finally`, ends the failed managed session and preserves stderr. Periodic immutable checkpoints remain every 100 completed updates; a normal bounded stop also retains the existing final-snapshot behavior (update ten for this diagnostic). Failed partial windows do not create a resumable checkpoint. Storage failure can prevent writing its own failure event; the original exception is preserved.
