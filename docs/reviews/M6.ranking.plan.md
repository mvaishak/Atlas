## Proposed first implementation: feature contract and parity gate

Implement a small shared `features/` module and ranker-input interface first. The
proposed feature recipe below needs lead approval before code; exact overlap and length
choices were not previously frozen. No dependency addition is proposed.

| Ordered feature | Proposed computation | Matrix dtype |
| --- | --- | --- |
| `bm25_score` | Existing full-corpus frozen Lucene BM25 score for this query/product | float32 |
| `dense_cosine` | Encoder-matched normalized-vector inner product using the selected native CPU subset scorer | float32 |
| `title_query_token_overlap` | Jaccard of unique tokens from the existing analyzer; empty union gives 0 | float32 |
| `query_token_count` | Analyzer token count, retaining repeated tokens | float32 |
| `title_token_count` | Analyzer token count, retaining repeated tokens | float32 |

No IDs, row positions, labels, split flags, group IDs, source RRF ranks or held-out
statistics enter predictors. Product identities are alignment metadata only. No scaling
or feature fitting is required. Missing catalog text follows the approved empty-string
policy; text-derived zero values are legitimate measurements, not guessed scores.
Dense scoring of an empty title still uses its actual encoder embedding. Missing product
identities or required scores fail closed; never substitute zero for unavailable scores.

A `FeatureBatch` should bind schema/version, ordered names, C-contiguous values of shape
(N,5), explicit missing masks, canonical product keys, query/encoder/bundle provenance and
text-empty metadata. In this complete five-feature recipe, required numeric values are
finite and masks are false; still persist and compare masks. Distinguish text emptiness
from numeric missingness. Future NaN-bearing features require a versioned contract,
not an implicit fill change. Sort rows by product key and retain an inverse mapping to
candidate order; use the same contract for training, offline scoring and HTTP prediction.

Both orchestration paths call shared computation, but parity tests must capture their
**actual inputs immediately before prediction**. Capture inside the lowest prediction
adapter, after any DMatrix conversion/column processing, at the call into the predictor.
A pre-conversion FeatureBatch alone cannot certify what the model consumed; compare
final input names, values, dtypes and missing semantics as well. Do not permit an
uncaptured second normalization or column transformation inside the adapter.

The fixture sequence is:

1. Run the offline evaluator on a pinned fixture candidate set; intercept the real
   ranker adapter boundary and copy the exact submitted `FeatureBatch`.
2. Exercise the actual HTTP route through `TestClient` with the same pinned CPU bundle,
   deterministic fixture encoder and same candidates; intercept that prediction boundary.
3. Join by product key and require exact names/order, shapes, dtypes, missing masks,
   text-empty metadata and values. Prediction tolerances cannot excuse feature mismatch.
4. Mutate the offline or serving orchestration in fixtures (column swap, normalization,
   dtype or row misalignment) and prove the gate fails. Calling the helper twice and
   comparing it with itself is insufficient.

Keep capture injection in test adapters, not a public feature/debug endpoint or a
production raw-query logger. Start with the existing zero-update Booster or a deterministic
fixture adapter to establish input correctness without claiming learned behavior. A real
fitted-model CPU integration check is separate and follows execution approval.

## Subsequent separately approved fitting/evaluation

For each available encoder, fit its own matched CPU XGBoost `rank:ndcg` model. Use
E=100/S=10/C=1/I=0, explicit `ndcg_exp_gain=false`, seed 42 and the pinned library.
Retain the independent zero-update NDCG fixtures and add objective/gradient-update sanity
checks only when modeling execution is approved. Report metrics with the existing E=1,
S=0.1,C=0.01,I=0 evaluator; the 100:10:1 labels preserve those ratios.

A small initial proposal is one fixed fit per encoder (no sweep): histogram trees,
100 boosting rounds, depth 4, eta 0.05, subsample/column sampling 1, lambda 1, alpha 0,
min-child-weight 1, CPU/thread count 1. These are proposed baseline settings, not optimal
or approved values. Do not choose rounds or seed after looking at development results.
Register all actual fits; the contract's proposed eight-fit ceiling is not permission
to spend those fits automatically. Training is train-only, development labels are for
reporting, and the official test remains locked.

Evaluation must preserve the existing meanings:

- **A:** score every judged development candidate, including those missing from retrieval;
  compare matched ranker with BM25/dense/RRF on that full fixed judged pool.
- **B:** leave full-catalog retrieval unchanged and retain its baseline results. Do not
  present reranked judged-pool recall as catalog retrieval.
- **C:** independently retrieve BM25 top 100 and matched dense top 100; use the existing
  top-100 RRF pool. Compute all five scores for those candidates (do not use “not in
  retriever top 100” as a zero cosine/BM25 score). Compare exactly the same pool before
  and after reranking; no judged positives are added and no unknown products removed.
  Save all candidate keys/output order, then select top 10 for the API.

Use existing product-key tie-breaking, full-judged IDCG and no-E exclusion handling,
known-exact recall/unknown caveats, and paired group bootstrap (2,000 resamples, seed 42).
Track C's Recall@100 must remain unchanged for a preserved 100-candidate pool; a gain
there would indicate changed membership or a reporting error. Pretrained and M5 pools
can differ, so label within-pool versus cross-pipeline comparisons explicitly.

The M5 historical padding/normalization/tie differences remain part of its lineage.
For a new ranker, register the exact shared CPU scoring recipe. Do not quietly equate
M5's historical NumPy Track A scoring to the native subset scorer or relabel newly
scored results as old M5 evidence. Resolve and document CPU/CUDA vector compatibility
for each available bundle before actual-model parity is claimed.

## Resources, dependencies and approval boundaries

Routine schema/parity tests use tiny synthetic CPU fixtures and no downloads, GPU,
cloud runtime or real dataset scan. No implementation has run during this plan.
The five-column training float matrix alone would be 6,733,880 bytes (~6.42 MiB);
training query vectors at 16,759×384×4 are ~24.55 MiB. These are array sizes, not total
RSS: native full-catalog vectors/indexes, lexical/catalog objects, XGBoost data/cache,
validation scans and Python overhead dominate memory. Stream features by whole query;
do not materialize every query-to-catalog combination.

Actual full feature generation/fitting/parity should use a tested Linux CPU environment,
not the unresolved combined Mac runtime. A provisional later resource request is
16 GiB available RAM at launch, 12 GiB worker RSS, up to 8 GiB scratch, 4 GiB new persistent
outputs and a two-hour wall cap. These are unmeasured proposal limits and confer no
execution permission. Reuse existing verified catalog vectors/indexes/model files;
no product re-encoding is required or authorized. Any private transfer of training
judgments/runtime allocation requires its own execution review.

Prerequisite gates: review outstanding source/lockfile history; verify the reference
Linux runtime; validate the selected original bundles; freeze feature/model recipes;
then request the exact full-run configuration. M5 actual-bundle checks remain blocked
on missing original artifact verification. Do not silently substitute an M4 encoder
for M5 or waive available-bundle parity to declare M6 complete.

## Acceptance and next decision

First implementation acceptance is exact feature/parity evidence, not relevance gains:
Unicode/whitespace, empty titles, ties, zero-IDCG groups, candidate permutations, batches,
save/load, corrupted models/schema/IDs, mismatched model/tokenizer/source and deliberately
broken feature order/normalization must be covered. No labels or IDs may leak into
predictors. Fixture tests must reach both independent prediction boundaries; CI remains
configuration-only until actually executed. Keep Mac test groups split to avoid the
known native conflict. Do not push or run GitHub Actions.

Later model execution acceptance additionally requires objective-update sanity, immutable
matched ranker bundles, actual pretrained/trained CPU-boundary checks, A/C reports with
same-pool paired uncertainty and unchanged B evidence. Neither a model win nor promotion
is assumed. A negative learned-ranker result must remain in the experiment record.

Alternatives considered: keep the already working RRF baseline (lowest risk, no learned
ranking evidence); introduce a new neural reranker (architecture/compute expansion,
rejected for this scope); or add the small shared-feature XGBoost path (recommended,
consistent with the frozen contract).

Human checkpoints: explain the five feature formulas and empty/missing policy; why
M5's E/I sampler is inappropriate here; why helper-vs-helper is not parity evidence;
why RRF candidates need full score recomputation; and why Recall@100 cannot improve
through reranking the same 100 identities. The user must review the feature definitions,
initial fit proposal, artifact/runtime gates and separate execution limits before code
or model fitting. This document records an audit/plan only; no ranker implementation,
training, official-test access, dependency change or new experiment was performed.
