## Architecture and changes

The flow is local approved CPU sample/model/source export, private Colab upload, inspected native CUDA environment, pinned dependency overlay, CUDA adapter, existing immutable chunk engine, verified persistent receipts, private return, local numerical checks and rebuilt CPU FAISS. No relevance judgments leave the Mac. All numerical/checkpoint/transport logic stays in `src/atlasrank`; notebook cells supply paths, mount the approved account and invoke package entry points.

The CPU configuration and `PinnedEncoder` implementation remain byte-identical. `CudaEncoder` inherits their model loader and reuses the model's tokenizer/pooling/normalization modules; it adds CUDA placement, deterministic float32 controls, timing and memory counters. The existing chunk engine adds a callback after each verified completed chunk, including skipped chunks, so persistence can fail before further encoding. Its artifact schema/scoring is unchanged. A separate adapter manages transport receipts and a ten-minute session ledger.

`colab_prepare`, `colab_environment`, `colab_runner`, `colab_pilot` and `colab_import` handle export/setup/execution/return. `evaluation/cuda_checks.py` adds proposed cross-device diagnostics, without changing evaluation metrics. The development evaluator accepts an explicit product recipe for imported CUDA vectors while retaining the actual CPU query recipe; shared semantic fields must match and reports record both. It retains the development-only loader, full source/title checks and frozen A/B metrics.

New reviewed configuration includes [CUDA recipe](../../configs/dense-cuda.json), [environment](../../environments/colab/environment.json), [hashed requirements](../../environments/colab/requirements.txt), [pilot proposal](../../configs/m4-colab-pilot.proposed.json) and [full-run proposal](../../configs/m4-colab-full-run.proposed.json). ## Immutable persistence and recovery

Completed chunks are sealed on the local POSIX workspace. A callback archives a chunk to a unique persistent ZIP, verifies reread archive/file hashes, then writes a receipt last. Receipt-backed objects are immutable; an interrupted upload is preserved but excluded. Job metadata/attempts are also receipt-backed. Restore validates receipts and reuses the existing source/recipe/interval/vector checks before skipping completed chunks.

A local synthetic interruption after the first acknowledged chunk was restored into a fresh workspace. Only the missing rows were encoded, and both chunk callbacks were exercised. Corrupted receipts/archive content, unsafe ZIP entries, changed source/configuration and incompatible recipe/backend fail closed. This is local filesystem evidence; no real Drive or CUDA interruption has run.

The persistent managed-session ledger charges setup, inference, warmup, checkpoints, failures and restarts. Unclosed sessions conservatively include downtime, which can exhaust the cap. Exclusive ownership requires an approved token and operator confirmation that the old runtime stopped. The transport assumes a trusted private source and operator; receipts aren't signatures or a distributed lock. Drive reread isn't proof of cloud durability. Require an independent download or fresh-runtime restore before full-run approval. Colab documents runtime deletion and Drive I/O/quota limitations. [Colab FAQ](https://research.google.com/colaboratory/faq.html).

## Five engineering questions and understanding checks

1. **Why preserve native Torch yet pin an overlay?** The Mac Linux lock selects CPU Torch. A reviewed CUDA-native build avoids accidental replacement, while explicit hashes/versions make the Python model stack inspectable; native compatibility still needs execution.
2. **What lets a checkpoint survive runtime loss?** A verified persistent chunk receipt plus matching job/source/recipe/identity. A local seal or unacknowledged upload alone doesn't qualify.
3. **Why can acceptable device outputs change top-k order?** Float32/library kernels can move near ties. Compare components and cosine errors, disclose cutoff/order changes and reject differences beyond the bound without changing evaluation metrics.
4. **Why record CPU query and CUDA product recipes separately?** They are distinct execution paths. Shared weights/tokenizer/semantics must match; backend-specific provenance must remain honest and development quality still needs measurement.
5. **What evidence would justify a full GPU budget?** Actual end-to-end rate including setup/persistence, memory and storage, numerical gates, independent checkpoint restore, exact identity coverage, native local FAISS validation and an approved cumulative ledger/destination. A GPU name doesn't supply those measurements.

Before approval, the lead should trace one product through source/token hashes, chunk manifest, persistent receipt, restored vector and native row; inspect failure/ownership/time guards; explain the cross-version tolerance and near-tie policy; review the native environment and exact private folder; and recompute storage/runtime requests from actual evidence.
