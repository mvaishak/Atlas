## Behavior and architecture

The existing `serving.app.create_app` remains the only FastAPI application. The original
`POST /search` handler, request schema, BM25 adapter and health/readiness responses are
preserved. An optional pinned comparison fixture adds read-only replay capability:

| Interface | Behavior |
| --- | --- |
| `GET /demo` | One HTML view with a local token stylesheet; no external services or UI framework |
| `POST /search` | Existing arbitrary-query live BM25 search; the view requests top 10 |
| `GET /comparison` | Five allowed development query IDs/texts and fixture identity |
| `POST /comparison` | Strict `{query_id: integer}`; original M3 BM25/M4 hybrid Track B top-10 lists |
| `/health/live`, `/health/ready` | Existing bodies/statuses unchanged; optional replay failure does not invalidate BM25 |

The view labels **Live Search** and **Saved Comparison** separately. Saved mode says
“not live neural inference”; only its five recorded queries can be selected. Live
mode displays actual measured BM25 search time. Saved mode shows historical timing
as **— unavailable**, and labels the newly measured replay lookup separately from
model latency. Unknown development judgments remain `unknown`. Live search does not
load judgments; its label status is explicitly unavailable. M5 has no result pane.

The fixture compiler verifies pinned M4 report/per-query hashes, protected development
inputs, frozen evaluation bytes and the validated lexical bundle. It streams report
records, selects the fixed IDs and needed product titles, verifies ranking/score
alignment and copies the original order and score values. It neither searches nor
recomputes fusion/metrics. Serving only loads the small fixture, whose SHA is supplied
separately by the operator. Typed schema, content identity, model/recipe provenance
and the loaded lexical bundle must agree. Missing/corrupt/incompatible fixtures return
503 `comparison_unavailable`; unknown IDs return 404; invalid request fields return 422.
No fixture failure changes `/search` or its readiness contract.

All API-derived text is rendered with DOM `textContent`; no query/title data is embedded
in HTML or assigned to `innerHTML`. A content security policy allows only the exact
inline script/style hashes and same-origin fetches. Hallmark now supplies a custom light/dark teal workbench theme, flat background surfaces and a subtle grid pattern. Theme choice persists in localStorage,
defaults to the OS preference and tolerates unavailable storage. Typography uses local
Avenir/sans and monospace fallbacks; no font service, Tailwind or React is installed.
The new user preferences supersede the earlier dark-only visual guide. Product IDs, titles and scores are preserved rather than reformatted by generic
style rules. The HTML is included in the existing Python wheel/package.

## Operator commands

The actual private fixture is already prepared. From the repository root:

```sh
.venv/bin/python -m atlasrank serve \
  --index data/esci/indexes/m3-bm25-v2 --port 8000 \
  --comparison .local/m6/comparison-v1.json \
  --comparison-sha256 fa1fae1d3a954af0825ddf6acde2553a323e73a073cf53d7888424cf510b1de0
```

Open `http://127.0.0.1:8000/demo` (or `/demo#saved`). The command retains loopback-only
binding and disables raw Uvicorn access logs. The original command without comparison
flags remains valid for live BM25. Both comparison flags must be provided together.
The smoke servers and isolated test-browser processes were stopped; no demo server
is left running by this review task.

To reproduce the fixture, use a **new** output path; extraction refuses overwrite:

```sh
.venv/bin/python scripts/prepare_demo_examples.py \
  --config configs/m6-demo.json --output .local/m6/comparison-reproduced.json
```

Its SHA must match the value above with the same pinned inputs. The default prepared,
lexical and report paths are explicit in `--help`. No artifact/model download occurs.
Do not change source pins to accommodate a mismatch without review.

## Alternatives, failure modes and remaining limitations

| Alternative | Decision |
| --- | --- |
| A second API/UI framework | Rejected: same app and one packaged HTML view suffice |
| Live neural inference on the Mac | Deferred: native Torch/FAISS conflict and original artifact verification remain unresolved |
| Serve the whole historical evaluation dataset | Rejected: compile a pinned five-query fixture under 1 MiB |
| Recompute or normalize historical ranks/scores | Rejected: copy original Track B lists and preserve empty/short behavior |

Hash, model/bundle, group, title-lookup or ranking/score mismatches stop extraction before
publishing a fixture. Runtime schema/hash failures disable only comparison capability.
Unknown selections and invalid JSON bodies have safe explicit errors. Source records and
prior artifacts are never overwritten. The UI reports failures rather than retaining
unlabeled stale results; no model weights or labels are loaded to answer a live query.

Full original M5 chunks/index/IDs/dense-hybrid rankings remain externally stored and not
independently verified here. M4/M5 product padding, normalization and dense tie-handling
differences remain limitations; this demo makes no weights-only or model-promotion claim.
The Mac native conflict, actual CUDA resume parity, full Linux CI and MPS remain unverified.
Earlier uncommitted M4/M5 prerequisites remain outside the M5.5 commit; this working-tree
implementation is not proof of clean-checkout reproducibility. No learned-ranker or
exact learned-feature matrix parity is implemented. Future M6 ranker gates remain intact.

## Understanding and review log

1. Why is Saved Comparison not live neural inference? Explain pinned record replay,
   allowed query IDs and the absence of model/index calls in the replay adapter.
2. How do you prove a displayed result is genuine? Trace input report hash → original
   rank/score/identity → canonical title → fixture hash → exact API response → DOM text.
3. Why are 79 results unknown? Only explicit judgments for the selected development
   query count; missing judgments do not establish irrelevance.
4. Which timing numbers are meaningful? Separate current BM25 search, replay lookup,
   unavailable historical search time and controlled benchmark evidence.
5. What would be required for M5/live ranker serving? Original artifact validation,
   compatible native runtime and exact offline/HTTP feature-boundary tests; this view
   proves none of those by itself.
