# M5 memory review v0.1 — proposed changes only

The failed L4 VM was released after reverifying the returned failure archive. Release accounting (`docs/reviews/M5.release.json`, private evidence) records 1,944.79 seconds (32m 24.79s) from the conservative pre-connect timestamp to UI-confirmed deletion. This includes setup, failed execution and idle inspection, remains below 3,600 seconds, and is an observed wall-allocation upper bound rather than Google billing telemetry. Original start/failure records and all M3/M4 history remain unchanged. No retry or new GPU allocation occurred.

## Assessment

**Proven:** the free-VRAM guard raised at `training/loop.py:92`, after an optimizer/scheduler update, before the first step-100 checkpoint/progress event. The exact update count remains unknown (1–99). No trained weights/checkpoint survived. Free VRAM at the failure was below 8 GiB, but its exact value, allocated/reserved amounts and peak were not logged. The post-exit 23.46 GB free snapshot cannot establish training memory use or growth across steps.

**Source audit:** `SharedMiniLM.loss` keeps the query forward graph alive while forwarding all products, then backpropagates both graphs together. Both towers share weights. Losses retained across batches are detached Python floats; there is no `retain_graph=True`, growing tensor cache, or tensor-valued history list. `backward()` releases saved activations; the previous scalar `loss` remains referenced until the next assignment, but this does not retain the backward-freed activation buffers. Token tensors and product embeddings are local to each call. The padded candidate matrix and normalization/logit tensors are small. Gradients remain after `optimizer.step()` until the next `zero_grad(set_to_none=True)`. AdamW initializes two persistent moment tensors on its first update, and CUDA implementations can require temporary optimizer buffers. These are expected allocations, not evidence of an accumulating leak.

The exact export has 9,180 groups in 574 effective batches. The first batch has **16 queries + 79 products = 95 text sequences**. Across the first 99 batches, product counts range from 64 to 94; the catalog-wide maximum per training batch is 94. All sequences are padded to 256 tokens, float32, eager attention. The final effective batch has **12 groups**, not four. MiniLM has 22,713,728 parameter elements: about 90.85 MB float32 weights, the same for gradients, and 181.71 MB for AdamW's two moments, excluding optimizer temporaries and activations. These persistent tensors alone are much smaller than the failure threshold.

Eager attention and FFN activations are the principal plausible footprint. For scale, a single float32 attention-shaped tensor at the theoretical 112-sequence maximum is 336 MiB per layer (`112*12*256*256*4`), before other saved tensors, dropout, backward and workspace. The product forward overlaps the saved query graph. Variable product counts can increase allocator reservation as larger batches arrive. PyTorch's caching allocator retains unused blocks; reserved memory can therefore keep driver-free memory low even after backward frees live activations. This is a hypothesis supported by the execution pattern, not a measured attribution. See [PyTorch memory-management documentation](https://docs.pytorch.org/docs/stable/notes/cuda.html#memory-management).

**Conclusion:** excessive per-batch activation/reservation footprint is the leading explanation. The code audit found no clear persistent autograd-history leak. Existing evidence cannot distinguish a first-batch peak from later growth, nor establish that peak allocated VRAM stayed under 10 GiB: the free-memory check raises before the allocated-peak check. No loss, throughput, exact peak or exact step values should be invented.

## Proposed smallest change

Keep the same 16-group effective batches and frozen sampled order, but split each into **microbatches of 8 groups with accumulation up to 2**. Retain all positives/negatives within each query group. For an effective window of N groups, backpropagate each microbatch mean multiplied by `microbatch_groups/N`; this preserves the equal-query mean, including the final 8+4 window. Zero gradients once per effective window, backward each microbatch immediately without graph retention, then clip once and perform exactly one optimizer/scheduler update. Keep the same 574-update schedule, seed, float32, model/tokenizer, temperature, optimizer, supervision and evaluation contract. Expected activation demand decreases approximately with sequence count; weights, accumulated gradients and optimizer state do not halve. Throughput and fit remain unmeasured. Active dropout and changed operation shapes mean numerical/trajectory equality to the original batch execution is not promised.

This is one proposed configuration, not a sweep. Preserve the 8 GiB free floor, 10 GiB allocated peak and all other limits. Do not use empty-cache calls, precision changes, allocator tuning, truncation changes, activation checkpointing or relaxed limits as an implicit workaround. An eight-group microbatch is not guaranteed to fit; a failed bounded check must stop.

## Proposed diagnostics and failure preservation

Decouple progress logging from the checkpoint interval. Emit scalar-only structured records at every effective update and each microbatch phase: before forward, after forward, after backward, and after update. Record run/session IDs, effective step and sampler cursor, microbatch index/group count/text count, phase, loss, pre-clip gradient norm when defined, LR, elapsed time/throughput, free/total/allocated/reserved VRAM, per-step and cumulative peaks, available host RAM and RSS. Use null for values not yet defined; nonfinite values produce explicit failure fields rather than invalid JSON. Synchronize only at declared diagnostic boundaries and measure logging/synchronization overhead.

Flush/fsync the completed-update event **before** the post-update guard. On exceptions, write a terminal failure event with last committed update/cursor, attempted phase, measured memory and exception; close logs in `finally`. Check memory after forward/backward as well as at update boundaries. Checkpoint cadence can remain 100 updates; never mark a partial optimizer window as committed or imply that a failure event contains resumable model state. No GPU tensors or graph-attached values may be stored in progress records. A bounded log budget of 8 MiB is ample as a proposal but must be measured within the existing persistent cap.

Start-of-step allocated-memory samples distinguish retained tensors from reservation: growth in allocated memory after consistent cleanup suggests retained live state; stable allocated memory with rising reserved/low free suggests allocator/workload high-water behavior. Phase peaks and text counts establish whether the smallest batches alone exceed the budget. A future separately approved diagnostic should run at most 10 effective updates with this single configuration and unchanged safeguards; it must not automatically continue into the full pilot.

## Bounded regression tests proposed for approval

1. Float32 synthetic, dropout disabled: accumulated 8+8 versus full 16-group loss/gradients and one AdamW update agree within predeclared `atol=1e-6, rtol=1e-5`; include unequal candidate counts and final 8+4 equal-query weighting. No cross-query negatives or sampler changes.
2. Synthetic dropout active: uninterrupted versus checkpoint/resume under the same accumulation configuration meets the existing 1e-7 parameter/optimizer-state criterion; exact update/scheduler/cursor equality; checkpoints only at effective-window boundaries.
3. Inject low free VRAM or a nonfinite loss/gradient at each phase: thresholds stay unchanged; a pre-update failure commits no update, a post-update failure durably records the completed update, and exception logs close without fabricating checkpoints.
4. Validate per-step JSON schema, finite-or-null fields, host/GPU memory distinctions, checkpoint/progress independence, fsync-before-guard ordering and absence of graph-attached tensors in retained history.
5. Preserve existing admissibility, summed-positive loss, deterministic-plan and checkpoint-integrity fixtures. Run Ruff, strict mypy and focused CPU tests. Actual CUDA memory trend/throughput tests remain unrun until separately authorized.

Only inspection, export-count arithmetic, archive integrity and release accounting ran for this review. No training code, approved manifest, model, loss, sampler or experiment settings were changed. The proposed patch, diagnostic execution and resource decisions await approval.
