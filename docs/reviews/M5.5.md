# M5.5 reproducibility closeout v0.1

M3–M5 source and available evidence are consolidated for review. No training,
full-catalog encoding, index rebuild or full retrieval evaluation ran in M5.5.
[Reproduction guide](../REPRODUCING_M3_M5.md), [frozen pins](../../configs/m5-reproduction.json),
validation (`docs/reviews/M5.5.validation.json`, private evidence) and evidence inventory (`results/m5_5/evidence-inventory.final.json`, private evidence)
identify executed checks, historical records and missing external artifacts separately.
M6 has not started. Completion of this engineering closeout does not promote a model
or establish complete independent verification of the manual Colab artifacts.

## Inventory and architecture

Existing working modules already cover canonical chunks, receipts/recovery, sealed
FAISS bundles, BM25 scoring, RRF, query metrics and grouped bootstrap. Training sources
already implement admissible train-only sampling, the summed-positive loss, weighted
microbatch accumulation, durable observations and full checkpoint/RNG restoration.
Those implementations and all training/model history are retained.

The remaining manual logic was in `.local/evaluate_m5_track_a.py`,
`.local/export_m5_bm25.py`, the saved `AtlasRank_M5_Full_Catalog_Encoding.ipynb` and the
user-supplied shared chat. M5.5 adds:

- `retrieval/m5_encoder.py`: local-only trained-model inventory checks and distinct
  historical catalog / fixed-query recipes, using the existing shared MiniLM and tokenizer.
- `retrieval/m5_artifacts.py`: read-only legacy chunk validation and a native-only index
  rebuild/validation entry point. It checks canonical rows/titles and reconstructed native
  vectors rather than trusting a count or checksum alone.
- `evaluation/m5.py`: development validation, Track A NumPy scoring, variable-length
  BM25 export, Track B metric/RRF replay and the existing grouped paired interval.
- `experiments/m5.py`: thin commands joining these modules. New canonical encoding
  delegates to `chunks` / `colab_full`; canonical FAISS build/load delegates to
  `dense_bundle`. Native and neural commands run in different interpreters.
- A thin unexecuted reproduction notebook, pins, a local evidence-audit script, numeric-only
  paired inputs, summary evidence and synthetic fixtures. No dependency changes.

Data flow is canonical label-free titles → trained encoder → immutable aligned chunks →
native CPU IndexFlatIP + IDs. Development-only queries are encoded separately; the native
worker joins frozen BM25 top-100 and dense top-100 through RRF-60 and existing metrics.
Track A scores the full judged candidate pool independently. Statistical replay consumes
matched numeric per-query observations and normalized-query groups, not raw labels.

## Scientific findings and compatibility audit

The guide records every exact metric and artifact hash. M5 dense A NDCG@10 is
0.7183348379701574 and MRR@10 is 0.7818716434664607, from the historical local aggregate.
M5 dense B Recall@20/@100 is 0.26216427198139103 / 0.430889276151662.
M5 hybrid B is 0.309062098376579 / 0.49398627992225863. Local compact observations
reproduce the B means and all four paired intervals. They do not independently establish
that the missing full rankings were generated and scored correctly.

Hybrid Recall@100's difference from M4 is +0.005054626370871675, 95% interval
[+0.0011339567463601959, +0.008991278255044432]. There are 641 improved, 578 worsened
and 2,910 unchanged queries. Dense standalone improvement is not statistically established.
This is a small development-only signal under incomplete judgments, with no training-seed
replication or official-test claim.

The saved notebook and shared chat reveal implementation differences: catalog ST.encode
length-sorts 1,024-title dispatches, dynamically pads batches of 32 and normalizes again;
queries use fixed 256. M5 B uses batched FAISS order without M4 cutoff-tie refinement;
A uses NumPy candidate scoring. Historical TF32/determinism and full encoding dependencies
were not recorded. FAISS 1.15.1, ST 6.1.0, L4 and the index hashes are present in saved
executed outputs. A newly recorded runtime is not retroactive evidence for the old run.
This is a pipeline comparison, not a strict weights-only ablation.

## Executed verification and failures

- The exact 142 MiB encoding ZIP, canonical catalog and every local trained model file
  pass pinned SHA checks. Configuration records exact byte sizes through the inventory.
- Protected development loading confirms 82,959 pairs / 4,129 queries / 4,129 groups.
  No official-test file was opened.
- All 4,129 saved BM25 lists match M4 identity and order exactly: 404,929 hits,
  102 lists shorter than 100, including 25 empty lists. No padding was introduced.
- Four grouped paired intervals independently recomputed with repository code match the
  historical intervals exactly. Last-bit macro-mean summation differences are disclosed.
- Retrieval/data/metric fixtures: 78 passed. Training fixtures: 41 passed, one CUDA-only
  resume test skipped. Other integration fixtures: 91 passed, two dependency warnings.
  Total: 210 passed, one skipped, run in three separate interpreters.
- Strict mypy passes across 96 source files. Ruff passes for `src`, `tests`, `scripts`
  and the new notebook. Formatting passes for the changed code/notebook.
- Broad Ruff has 106 pre-existing violations in five historical training notebooks;
  broad format checking also identifies those five snapshots. They remain preserved.
- Initial broad integration checking found eight failures in the M4 gate-order fixture:
  it compared a historical proposal to the current expanding source inventory. Only that
  test fixture now stubs the historical inventory. It still rejects bad source pins and
  every frozen setting. Production guards and historical proposals were not modified.

The [guide](../REPRODUCING_M3_M5.md#tests-and-known-environmental-limits) gives exact
commands. Machine-readable validation links local logs, hashes and unrun work. No combined
Mac Torch/FAISS retry, dependency installation, remote, CI run, cleanup or publication occurred.

## Failure modes and residual gaps

Hash mismatch, missing files, invalid schemas, non-development partitions, duplicate
query/product IDs, row gaps, reordered titles, incomplete indexes, changed recipes,
non-finite vectors and mismatched paired eligibility fail closed. New outputs refuse to
overwrite existing paths. Failed partial new builds remain for inspection. New sealed
encoding uses existing immutable publication/receipt recovery; tiny interrupted/resumed
fixtures verify completed chunks are not replayed.

Full M5 Drive chunks, index, IDs and dense/hybrid ranking files are not locally available.
Their hashes are notebook-reported, not independently rehashed in M5.5. Full M5 vector
norm/alignment validation and relevance recomputation from the original rankings remain
unexecuted. A's historical candidate rankings are missing. Complete historical encoding
runtime and CUDA-resume parity remain unverified. Full Linux CI, MPS and resolution of
Mac OpenMP remain outstanding. Root RTK.md and PROCESS.md references could not be found
in the available repository/local instruction paths; no instructions were invented.

## Interview questions and human-understanding checks

1. Why can A improve while B dense Recall@100 falls? A ranks the judged pool; B must
   find known E products in 1.2 million candidates. Training and incomplete judgments
   can affect those tasks differently. Explain both actual score paths.
2. What does the hybrid CI establish? A small conditional development/query-sampling
   difference for one experiment. It does not prove dense improvement or broad relevance.
3. Why does a correct vector count not prove a valid index? Permutations can preserve
   count and norms. Explain canonical keys, chunk ranges and native reconstruction checks.
4. Why are CUDA embeddings not guaranteed bitwise reproducible here? Kernel dispatch,
   batch padding, reduction order and unrecorded TF32 settings can affect near ties.
   Trace the product/query recipe differences without changing the historical records.
5. Why are short BM25 lists retained? Zero lexical matches are not meaningful candidates.
   Explain RRF rank inputs, unknown judgments, recall denominators and no-E exclusions.

The lead should inspect one multi-positive loss fixture, the final 8+4 accumulation
weighting, chunk resume validation, original-versus-new schema separation and the paired
bootstrap command. Explain why numeric replay is weaker than full ranking verification.
Generated answer outlines do not establish human understanding or approval.

chat. The agent audited those sources, added adapters/commands and synthetic tests, reproduced

still reviews the changes and explicitly authorizes the next milestone.

prediction, and label unknown development judgments accurately. Do not present unrun M5
hybrid A or test results. API expansion, an interactive comparison demo and environment
repair require their own approved scope. No M6 code is included here.
