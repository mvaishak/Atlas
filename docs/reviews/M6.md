# AtlasRank M6 — Final Engineering Review

**Milestone:** M6 — Learning-to-Rank  
**Status:** Development evaluation completed; engineering review finalized  
**Training runs:** 1  
**Evaluation queries:** 4,129  
**Test partition:** Locked, not evaluated  
**Execution protocol:** Checkpointed, multi-stage execution (documented deviation)

---

## 1. Executive Summary

M6 introduced a supervised learning-to-rank (LTR) stage into AtlasRank, using XGBoost to rerank products retrieved from the Amazon ESCI catalog. The objective was to determine whether combining lexical, dense retrieval, and query-document features in a learned ranking function could improve relevance over the frozen BM25, dense, and hybrid baselines.

**M6 successfully improved ranking performance on judged development candidates (Track A), but failed to improve ranking quality on the end-to-end retrieval candidate pool (Track C).**

On Track A, the ranker achieved an NDCG@10 of **0.711080** and MRR@10 of **0.772119**, outperforming all three frozen baselines. All six paired-bootstrap confidence intervals for these comparisons were positive.

However, on Track C, the same ranker achieved an NDCG@10 of **0.244565**, compared with **0.247935** for the original reciprocal rank fusion (RRF) ranking. The observed NDCG regression was small but its 95% paired-bootstrap confidence interval excluded zero.

The experiment therefore demonstrates an important distinction between optimizing relevance within a supervised candidate set and improving ranking performance over candidates retrieved from a large catalog.

M6 is considered **complete as an engineering and development-evaluation milestone**, with clear limitations documented. The evidence does not support claiming an end-to-end ranking improvement or production readiness.

## 2. Objectives and Scope

M6 aimed to establish a reproducible learning-to-rank baseline without modifying earlier retrieval components.

The experiment was designed to answer two questions:

1. Can a supervised XGBoost ranker outperform frozen BM25, dense, and hybrid baselines when ranking the same judged candidates?
2. Can that ranker improve the ranking of candidates retrieved by the existing BM25-plus-dense pipeline?

These questions were evaluated separately to avoid conflating reranking quality with candidate retrieval quality.

The frozen M3 BM25 index and M4 dense retrieval artifacts were preserved throughout the experiment. The M6 ranker was trained using the predetermined feature schema and hyperparameter configuration, with no additional model fitting or hyperparameter tuning.

## 3. Experimental Setup

### 3.1 Dataset and artifacts

The experiment used the US portion of the Amazon ESCI product-search dataset and the frozen AtlasRank retrieval artifacts.

### 3.2 Feature engineering

Each query-product pair was represented using five features:

| Feature | Purpose |
|---|---|
| `bm25_score` | Lexical relevance |
| `dense_cosine` | Semantic similarity |
| `title_query_token_overlap` | Query-title token overlap |
| `query_token_count` | Query length |
| `title_token_count` | Product-title length |

Features were generated using the original AtlasRank implementation, preserving the same retrieval context and feature definitions used by the frozen experiment configuration.

The feature schema was not modified during training or evaluation.

### 3.3 Model configuration

The ranker used the fixed XGBoost `rank:ndcg` objective with `ndcg_exp_gain=false`.

The configuration included:

- Histogram-based tree construction
- Maximum tree depth of 4
- Learning rate of 0.05
- 100 boosting rounds
- No early stopping or hyperparameter search
- CPU execution
- Deterministic random seed of 42

Exactly one complete model fit was recorded.

The final trained model was saved in XGBoost's native UBJ format and verified against its recorded SHA-256 hash.

## 4. Evaluation Methodology

### Track A — Judged-Candidate Reranking

Track A evaluates the ranker's ability to order products already present in the development judgments.

Each method operates on the same judged query-product candidate set, allowing a controlled comparison of ranking functions.

M6 was compared against three frozen baselines:

- BM25
- Dense retrieval
- Hybrid retrieval

The primary metrics were NDCG@10 and MRR@10.

Because candidates are drawn from the judged set, this track has complete judgment coverage. However, it does not independently establish performance over arbitrary products retrieved from the full catalog.

### Track C — Retrieved-Candidate Reranking

Track C evaluates the ranker under a more realistic retrieval setting.

For each development query:

1. Retrieve the top 100 BM25 candidates.
2. Retrieve the top 100 dense candidates.
3. Combine the lists using reciprocal rank fusion with `k=60`.
4. Retain the top 100 fused candidates.
5. Apply M6 to rerank that exact candidate pool.
6. Compare the original RRF ordering against the M6 ordering.

The candidate pool is identical before and after reranking.

This design isolates changes in ranking order from changes in candidate generation.

The evaluation measures NDCG@10, MRR@10, known-exact Recall@20, known-exact Recall@100, and judgment coverage.

### Statistical analysis

Paired-bootstrap comparisons used:

- 4,129 development query groups
- 2,000 resamples
- Random seed 42
- Ten prespecified metric comparisons

Reported 95% confidence intervals were derived from the original AtlasRank evaluation implementation.

These intervals characterize variation in the observed, judgment-based evaluation. They do not correct for missing relevance judgments or multiple comparisons.

## 6. Analysis of the Track A–Track C Gap

The most important finding is that the ranker's effectiveness depends on the candidate distribution.

Track A and Track C differ in both candidate composition and relevance-label availability.

### 6.1 Candidate-distribution mismatch

Track A contains products drawn from relevance-judged query-product pairs. Track C contains products selected by lexical and dense retrieval from a catalog of more than 1.2 million products.

The features that distinguish highly relevant products from judged negatives may not behave identically on retrieved candidates that were absent from the training judgments.

This is a plausible form of training-to-inference candidate-distribution shift.

However, the available aggregate metrics alone cannot establish whether feature-distribution shift is the primary cause. That requires query-level and feature-level analysis.

### 6.2 Sparse judgments in the retrieved pool

Track A has complete judgment coverage, while Track C has only approximately 7.37% judgment coverage within its top-100 results.

At rank 10, judgment coverage decreased from 25.16% under RRF to 24.34% under M6.

This is an important observation: M6 promoted slightly more unjudged candidates into the top 10.

However, **unjudged does not necessarily mean irrelevant**.

The benchmark cannot establish whether the promoted products were genuinely irrelevant, reasonable substitutes, or relevant products missing from the ESCI judgments.

Consequently, part of the measured performance difference may reflect incomplete judgment coverage rather than actual user-facing relevance.

The existing results establish a regression under the current evaluation policy, not a definitive regression in true relevance.

### 6.3 Candidate-generation bottleneck

Track C's known-exact Recall@100 is approximately 0.489.

The same value is observed for RRF and M6 because the two methods rank identical candidates.

This indicates a retrieval-stage limitation: many known exact-relevance products are absent from the final top-100 candidate pool.

A reranker cannot recover a relevant product that was never retrieved.

Improving candidate generation may therefore provide greater potential benefit than increasing reranker complexity alone.

### 6.4 Missing retrieval-position information

The five-feature ranker uses lexical and semantic scores, token overlap, and text-length features.

It does not explicitly incorporate the BM25 rank, dense rank, RRF score, or an indicator of which retrieval system supplied each candidate.

One hypothesis is that the fixed feature schema does not preserve enough of the strong ordering signal already captured by RRF.

This is not proven by the current results, but it is a concrete direction for future experiments.

### 7.2 Execution-protocol deviation

The original M6 execution plan expected a single bounded run covering feature generation, model fitting, and development evaluation.

This proved impractical within the available Colab execution conditions and time budget.

The implementation was therefore adapted to three checkpointed stages:

1. Persistent feature generation and assembly.
2. One fixed-configuration model fit.
3. Resumable development evaluation.

The original training features, hyperparameters, frozen retrieval artifacts, and evaluation definitions were retained.

This enabled the experiment to complete without repeated training or loss of expensive intermediate results.

**The checkpointed execution is a protocol deviation and must not be described as a successful execution of the original single-run time contract.**

### 7.3 Recovered provenance

The original input manifest was lost during an earlier runtime reset.

Subsequent recovery validated the original frozen bundle identities, prepared dataset integrity, model hash, feature schema, and pinned inference environment.

The final model was packaged with reconstructed provenance metadata and successfully loaded through the project's model-validation interface.

This supports integrity and reproducibility of the recovered artifacts, but does not fully restore the missing original execution record.

### 7.4 Runtime dependencies

The final inference environment used the required CPU-only PyTorch build (`2.14.1+cpu`), BM25S `0.2.14`, XGBoost CPU `3.1.1`, FAISS CPU `1.15.1`, and the fixed MiniLM dependency versions.

The final verification passed without retraining.

### 7.5 Remaining reproducibility limitation

The current evidence supports successful model loading and completed development evaluation.

It does not independently establish deployment latency, throughput, memory performance under production workloads, or a fully automated clean-machine reproduction.

These remain separate engineering concerns.

## 8. Threats to Validity

**Incomplete relevance judgments:** The low Track C judgment coverage limits conclusions about actual relevance for retrieved products.

**Candidate-distribution differences:** Track A and Track C evaluate different product distributions, making direct comparison of their absolute metrics inappropriate.

**Multiple statistical comparisons:** Ten paired comparisons were reported. Confidence intervals are interpreted individually and were not adjusted for multiplicity.

**Development-only evidence:** All reported model comparisons use development data. The official test partition remains locked.

**Missing original execution manifest:** The recovered artifact provenance is verified, but the original complete execution record is unavailable.

**Unmeasured serving characteristics:** The experiment does not establish production latency or throughput.

**Unresolved regression mechanism:** Aggregate results suggest several plausible explanations for Track C degradation, but no causal mechanism has yet been demonstrated.

## 9. Engineering Conclusions

M6 achieved its primary objective of implementing and evaluating a supervised learning-to-rank system on top of frozen lexical and dense retrieval components.

The model successfully learned a ranking function that outperformed BM25, dense, and hybrid baselines in the controlled judged-candidate evaluation.

However, the model did not improve the observed ranking quality of the broader retrieval pipeline. Under the evaluated RRF candidate pool, its NDCG@10 was slightly worse, and its known-exact Recall@20 also declined.

The evidence therefore supports three conclusions:

1. **Supervised learning-to-rank is effective on the judged candidate distribution.**
2. **Judged-candidate gains do not automatically transfer to retrieved-candidate ranking.**
3. **Candidate generation, judgment incompleteness, and candidate-distribution mismatch deserve investigation before further reranker optimization.**

M6 should be considered a successful completed experiment, not a demonstrated end-to-end retrieval improvement.

## 10. Recommended Next Milestone — M7

The immediate priority should be understanding the observed regression rather than training another model.

### M7.1 — Query-level failure analysis

Compare queries where M6 improves Track A but degrades Track C.

Inspect changes in:

- Relevance ordering
- Known exact-product positions
- Judgment coverage
- Promotion of unjudged products
- Retrieval-source composition
- Query length and lexical overlap

The deliverable should be a reproducible failure taxonomy with representative examples.

### M7.2 — Retrieval and feature diagnostics

Investigate whether the fixed feature schema generalizes poorly to retrieved candidates.

Compare feature distributions between the judged training pairs and real retrieval pools, and examine whether M6 systematically demotes candidates that RRF ranks highly.

### M7.3 — Improved candidate-aware ranking

Only after completing the diagnostics, consider a separately versioned experiment involving retrieval-rank features, RRF signals, retrieval-pool-aware negative sampling, or a guarded fallback to the original RRF ordering.

These experiments must not retrospectively alter the frozen M6 result.

### M7.4 — Reproducible serving and evaluation

Create a clean bootstrap and reproducible inference workflow, add latency and resource measurements, and preserve the final evaluation artifacts.

Any future model-selection experiments should define their validation protocol in advance and avoid tuning on the locked test set.

**Decision: M6 development milestone complete.**

The original trained ranker and its development evidence should remain frozen.

**Result:** Improved judged-candidate ranking; no demonstrated end-to-end retrieval-ranking improvement.

**Recommended next action:** Perform query-level failure analysis using the existing saved outputs before making architectural or training changes.
