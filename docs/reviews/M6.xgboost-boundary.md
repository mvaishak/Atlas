## Implementation and data flow

The existing offline entry point and real `/rerank` FastAPI route remain unchanged.
The test injects a Linux-only zero-update predictor into the existing fixture adapter:

```text
offline_predict ─┐
                ├→ shared five-feature batch → existing final_input
HTTP /rerank ───┘    → ZeroUpdateModel.convert → native DMatrix
                     → capture_native → assert exact contract → Booster.predict
```

`ranking/xgboost_boundary.py` imports XGBoost only after a Linux guard. It requires
XGBoost 3.1.1. The Booster has `rank:ndcg`, `ndcg_exp_gain=false`, CPU/one thread,
base score 0.5 and **zero updates/trees**. No labels, objective updates, fit/train calls
or encoder inference are used. It is a validation-only fixture; no new learned-model
loader or serving pipeline is introduced.

The native snapshot reconstructs values from CSR presence using `DMatrix.get_data()`.
Absent cells start as NaN. It never uses dense `toarray()` to turn absent cells into
legitimate zeros. Native names, float feature types, float32 data, dimensions, values,
missing masks and the row/product sidecar must match the existing `PredictionInput`.
The original submitted dtype is checked too: DMatrix's implicit float64→float32 cast
cannot excuse an upstream dtype change. Native `float` type metadata and actual
float32 storage are recorded separately.

Product identities are not XGBoost predictors or a native DMatrix feature. The adapter
keeps them as an explicit row sidecar; permuted rows must retain matching keys. This
checks the conversion boundary, not the authenticity of a real catalog or encoder.
The original trusted-bundle prerequisite remains unchanged.

The Linux tests use the same four-product synthetic BM25/native-dense fixture and
existing sealed deterministic artifact loader. They independently call offline
prediction, then HTTP with a different candidate order, and capture after native
conversion immediately before `Booster.predict`. Zero-update save/load is exercised.
The HTTP response remains explicitly `learned: false`; its fixture pipeline label does
not claim a learned relevance model.

Deliberate native-conversion defects cover swapped values, swapped names, float64
submission, `missing=0`, NaN substitution and mismatched row identities. Each must
return the existing contract-failure response without a second native prediction.
Synthetic source/model hashes, explicit zeros and hand-calculated columns are checked.

```sh
python scripts/check_xgboost_boundary.py --output .local/m6-linux-boundary/linux-v1
```

`python` must be that existing environment's interpreter. The output directory must
not already exist. Source modules currently uncommitted from M4/M5 are prerequisites;
do not assume the feature commit alone contains them. The runner records source and
configuration hashes, including the working dependency files; it does not certify
that the outstanding lockfile/source history has been reviewed.

Bounds: CPU only, one native math thread, 180 seconds worker wall time, sampled 2 GiB
worker RSS stop (100 ms polling). This is a process safeguard, not a kernel-enforced
memory reservation. The workload is only tiny fixtures, with no large model/index
output. Autoloaded Pytest plugins and inherited `PYTEST_ADDOPTS` are disabled to keep
the selected suite stable. No Torch is imported; the positive native test asserts this.

The runner retains `pytest.log`, `junit.xml`, synthetic temporary bundles,
`native-boundary.json` and final `validation.json` (versions, source/evidence hashes,

skips/errors/failures**, plus actual native-boundary evidence, before reporting success.
Timeout, memory breach, native crash or incomplete evidence is a failure, with partial
logs preserved. Use a new output directory for a separately authorized retry.

Review `validation.json` and JUnit results; passing local reconstruction guards or a
